# Aurekai — business, public platform and retained distribution lineage

**Aurekai is the digital operating business and public network. Bonfÿre is the native institutional engine underneath it.** They are not two names for the same CLI.

AI agents can produce software faster than conventional planning, handoffs, approvals and integration processes can absorb it. Aurekai's operating model invests engineering time, AI computation, reusable software, institutional knowledge and distribution into digital assets, applications and opportunities. Bonfÿre makes the underlying work **composable, authorized, testable and reusable**. Each project should strengthen the capability base for the next.

"Digital private equity" describes a method of creating value through software and engineering rather than only cash. It is **not** a claim that Aurekai operates a regulated fund or owns businesses, publications or products that participate independently.

| | Aurekai | Bonfÿre |
|---|---|---|
| Role | Business, product network, estate, creator/public participation, commercial delivery | Canonical native runtime, semantic owners, work, authority and evidence |
| Investment | Developer hours, models, compute, existing software, data relationships, distribution | Retained capabilities and reliable execution circuits |
| Output | Work, Life, Live, Shop, customer software, partnerships and reusable product opportunities | Matrix identity, CapabilityClosure, WorkGraph, EffectKernel, receipts and public release owners |
| Acceptance | Published experience, customer workflow, signed terms and actual economic outcomes | Tests, explicit source revisions, independent witnesses and destination readback |

## What this `Aurekai/` directory actually contains

This directory is an **earlier Aurekai-branded CLI, continuity kernel and distribution/package lineage** preserved within the Bonfÿre source tree. It is not the canonical definition of the modern Aurekai business or the public deployment platform.

The older implementation has real source that can be inspected: `bin/akai.mjs`, `src/`, `kernel/`, `native/`, `registry/`, `schemas/`, `tests/`, `Makefile`, and `package.json`. Its package metadata identifies **`@aurekai/runtime` version `0.8.0-alpha.1`**, using Node/Bun-era packaging and compatibility manifests. That is the version defined in this directory, not a claim about the contemporary Bonfÿre system version.

| Part | Purpose in this lineage | Boundary |
|---|---|---|
| `bin/akai.mjs` | Legacy `akai` command/front door | Not the modern native Bonfÿre CLI source of truth |
| `src/continuity-core.mjs` | Prior continuity execution/projection implementation | Inspect source and tests before using as a dependency |
| `kernel/` | In-repo independent-kernel package experiment | A package boundary, not evidence of a completed external split |
| `registry/integrations.json` | Older adapter and protocol target registry | Descriptors and targets are not installed, authorized integrations |
| `src/render-manifest.mjs` and `Makefile` | Legacy bundle and compatibility-manifest packaging | Generated files are not proof of a current supported downloadable release |
| `docs/KERNEL_REPO_SPLIT_EXECUTION.md` | Explicit proposal and steps to extract the old continuity kernel | Do not infer the split or registry publication already occurred |

Older `.akmodel`, `.aksae`, `.akfpqx` and `.bf*` aliases exist in this lineage as compatibility-format names. They do not override the current native owner contracts, retained artifacts or the current model/compute infrastructure.

## Inspect or test the old package intentionally

From this folder:

```sh
cd Aurekai
node ./bin/akai.mjs --help
node --test tests/*.test.mjs
```

These commands exercise a **historical source package**. They are not an installation guide for the four public Aurekai destinations, and they make no guarantee that its former model files, external services, credentials or bundled runtime targets remain available. Read `package.json` and tests before installing dependencies. Do not use this checkout as an excuse to import stale semantic owners back into the current runtime.

The older README advertised npm, PyPI, container, Homebrew, Hugging Face, VS Code, Helm and GitHub distribution targets. Those were part of that package/rollout design; **the presence of a target name or manifest does not verify a current published package, active partner account or supported release**.

## Current engineering truth

Bonfÿre's architecture distinguishes stable subject identity, institutional authority, external observations, typed capability closure, WorkGraph work, resource/financial admission, native or agent realization and evidence. Agents and providers are carriers, not semantic owners. The latest source and current development runtime can be at different revisions, and public destinations require separate deployment readback.

**The delivery loop:** source or need → qualification → retained capability and missing-work plan → authorized implementation → independent verification → reusable improvement.
