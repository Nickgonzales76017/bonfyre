# Aurekai and Bonfÿre: business, project, technical model

**One thesis:** AI can produce software faster than traditional organizations can plan, coordinate and integrate it. The scarce capability is now retaining context, composing reliable systems, authorizing effects and turning each delivery into reusable capital.

| | Aurekai | Bonfÿre |
|---|---|---|
| Role | Digital investment and operating business; public products and distribution | Native software engine and institutional execution infrastructure |
| Invests | Engineering time, AI compute, reusable applications, integrations, knowledge and distribution | Durable identities, typed capabilities, WorkGraph, authority, effects, evidence and runtime |
| Builds | Work, Life, Live and Shop experiences; customer and partner applications; commercial programs | Source and identity owners, native commands, compilers, data/model/media systems, agents and verified execution |
| Value | More useful assets, services, software and participation; potential commercial returns | Less rework, reliable composition, controlled execution and reusable capability |
| Truth | Published product evidence and actual commercial receipts | Source, tests, immutable receipts, authority checks and live readbacks |

**Digital private equity is an analogy, not a claim to operate an investment fund or own every participating business.** Relationships may involve independent use, services, licensing, revenue sharing, partnerships or owned assets. A prospect, provider integration, proposal, signed agreement, invoice and collected payment are different things.

## Why this exists

Waterfall and Agile evolved around expensive, scarce human implementation. Agentic software can generate prototypes, tests, migrations and entire components in parallel; human planning queues, fragmented departments, repeated meetings and lost institutional context can become the bottleneck. Small teams often lack specialist knowledge even when they can generate code quickly. Unresolved design decisions become downstream integration and security debt.

Aurekai's target workflow is **goal → retained knowledge → existing capabilities → missing-work plan → bounded execution → independent verification → reusable improvement**. Humans direct goals and consequential decisions; routine transfers of context should not require a meeting. More generated code is not an outcome unless it is integrated, authorized, observed and maintainable.

## The compounding loop

1. **Discover** a customer need, public source, opportunity or internal system gap. Retain provenance and separate observation from permission.
2. **Qualify** desired outcomes, constraints, costs, legal rights, existing components and evidence needed for acceptance.
3. **Invest** developer hours, models, compute, domain expertise and reusable software rather than starting each project from zero.
4. **Compose and build** through native capabilities, typed contracts, source-owning applications and the appropriate execution environment.
5. **Verify** functional tests, authorization, source lineage, target-system readbacks and actual commercial effects.
6. **Reuse** improvements across the estate and distribute through Aurekai Work, Life, Live, Shop and partner destinations.

Compounding is a goal, not an automatic result. Reuse must preserve license, identity, authority, quality, cost and target-specific constraints.

## Technical cut

```text
goal or external observation
  → canonical source / subject / institution
  → contract + capability closure + resource plan
  → WorkGraph + authorized effect boundary
  → native / model / agent / external realization
  → execution receipt + independent evidence
  → reviewed release and reusable capability
  → Aurekai product, partner or commercial outcome
```

Bonfÿre owns the reusable operating mechanisms. Applications retain their own data and action contracts. Foreign-source observation never implies ownership or write permission. A model's proposed action never constitutes approval. A passing local test never proves a public deployment. A quoted amount never proves revenue.

## README and release evidence contract

Each public repository must identify its **role**, **specific use case**, **actual source status**, **entry point**, **tests or observable witnesses**, **dependencies and limitations**, and **current owner/canonical lineage**. Use these states precisely:

- **Demonstrated** — can be followed in a named sample, with its data and limits stated.
- **Implemented** — source and tests exist in the identified version; say which version.
- **Measured** — a specified test/measurement and witness exists; do not extrapolate.
- **Deployed / live** — a specific destination was read back, not merely compiled.
- **Declared / planned** — intent or architecture only; not a shipping capability.
- **Historical extraction** — useful prior code; not the present integrated runtime.

The public Bonfÿre `main` branch may lag local integration and release work. The current local architecture atlas and hypervisor counters are development-state observations, **not proof that the public GitHub branch, external integrations, or four public destinations run the same revision**. Keep this distinction whenever quoting a count.
